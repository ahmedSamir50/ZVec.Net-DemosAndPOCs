01 / Foundations

What is Vector Search?

menu_book 01 / Foundations

What is Vector Search?

find_in_page Keyword Search

Keyword / Lexical Search

SQL: WHERE body LIKE '%error%'

Matches exact strings and wildcards. Fails when vocabulary shifts.

"System crash" ✗ "Application breakdown"

These two phrases mean the same thing but share zero keywords — keyword search returns nothing.

hub Vector Search

Vector / Semantic Search

cosine(query_vec, doc_vec) → 0.94

Matches meaning. Synonyms and paraphrases land close in vector space.

"Network issue" ✓ "Connection timeout"

These phrases share no keywords but mean similar things — vector search finds the match.

Three ingredients
memory
Embedding model

Turns text/image/audio into a fixed-length float vector (384–1536 dims).

calculate
Similarity metric

Cosine, L2, or dot product — measures distance in vector space.

speed
ANN index (HNSW)

Graph structure for sub-millisecond top-K nearest-neighbour search.

ZVec.NET · Internal Tech Session 02 / 22
notes Speaker notes
If you search our knowledge base for "system crash" with a SQL LIKE query, you won't find a doc titled "application breakdown" — even though they mean the same thing. Keyword search is dumb about synonyms. Vector search turns text into numbers — a float array called an embedding — and measures geometric distance. Synonyms land close together in vector space, so "system crash" and "application breakdown" become nearby points. The search finds the match. There are three ingredients: an embedding model converts input to vectors, a similarity metric — cosine, L2, or dot — measures distance in that space, and an ANN index like HNSW makes the search fast enough for production, fast top-K queries at modest scale (often sub-ms warm, in-process). Now let's see where we'd actually use this.

03 / The Problem

The Infrastructure Bottleneck

warning_amber 03 / The Problem

The Infrastructure Tax of Vector Search

Every team that wants to ship a vector feature hits the same wall. The database itself is fast — it's everything around it that hurts.

network_check
Friction 01
Network Overhead

Every query is an HTTP/gRPC round-trip to a separate cluster. 5–30ms added latency on every search — even when the index lookup itself takes 1ms. Serialization, TLS handshake, connection pooling — all overhead you didn't have before.

settings_suggest
Friction 02
Operational Complexity

The usual reach: Qdrant, Weaviate, LanceDB, Postgres + pgvector, or Pinecone / Azure AI Search. Another Docker cluster (or cloud account) to deploy. Access keys to rotate. Firewalls to configure. Version upgrades to schedule. A monthly bill to justify.

shield
Friction 03 · Critical
Security Boundary

Sensitive records leave your application process. Customer data, internal docs, proprietary code — all shipped over the wire to a third-party service. For regulated industries or internal-only data, this is often a non-starter.

What if we could get vector search without Qdrant, pgvector, LanceDB, or a cloud account?→

ZVec.NET · Internal Tech Session 04 / 22
notes Speaker notes
Vector search itself isn't hard — the algorithm is well-understood and the libraries are mature. What's hard is the infrastructure tax that comes with it. Network overhead — every query pays a round-trip tax to a separate cluster, often five to thirty milliseconds, which usually exceeds the actual search time. Operational complexity — teams usually reach for Qdrant, Weaviate, LanceDB, Postgres plus pgvector, or Pinecone / Azure AI Search — another system to deploy, monitor, upgrade, and debug when it breaks at 3am, plus access keys to rotate and a cloud bill to justify. Security boundary — this is the one most teams underestimate. If you're searching over customer support tickets, internal financial docs, or proprietary code, shipping those vectors to a third-party vector DB means shipping sensitive data outside your trust boundary. For many of our use cases, that's a hard no. So I went looking for a way to do this in-process. That's what ZVec.NET is.

Be honest about the trade-off. Left side is ZVec.NET in-process. Right side is the usual alternative stack — Pinecone or Azure AI Search in the cloud, or self-hosted Qdrant / Weaviate / LanceDB / Postgres plus pgvector. In-process wins on latency, ops simplicity, and cost — but it caps out at single-node scale, roughly millions of vectors per machine. And the same SDK runs on Android — you can ship an offline RAG app on a phone.

ZVec.NET · Internal Tech Session 07 / 22
notes Speaker notes
Let's walk the eight index types. HNSW is the default workhorse — sub-millisecond search, 95 to 99 percent recall, works on every runtime we ship. Flat is exact brute force — keep it for tests and small datasets where 100 percent recall matters. IVF clusters vectors into Voronoi cells and lets you tune nprobe to trade recall for speed at scale. HNSW-RaBitQ is a quantized variant — smaller memory footprint, but it only runs on x86_64 with AVX2. DiskANN is for datasets bigger than RAM, Linux with libaio only. Vamana is another graph-based ANN that ships with the engine. Invert indexes scalar fields so your typed filters are fast. FTS is full-text search with BM25-style ranking. Product-search (`examples/03-product-search`) is the live demo for Invert + FTS on one typed collection — colour/season/gender filters plus hybrid dense+FTS. The two platform limits are real and the SDK handles them gracefully — it throws PlatformNotSupportedException before the native call, so you get a clean .NET exception with a helpful message instead of a native crash.

In-DB Rerankers — No Extra Service

Two rerankers execute natively inside ZVec:

  • ZVecRrfReranker — Reciprocal Rank Fusion across sub-queries (e.g. title_vec + body_vec).
  • ZVecWeightedReranker — Weighted fusion (e.g. dense 0.7 / FTS 0.3).
Multi-Query Overload

ZVec.NET · Internal Tech Session 08 / 22
notes Speaker notes
Three metrics, one enum — and Metric is the second slot on [ZVecVector] (we fill the whole attribute on the Getting Started slide). Cosine is your safe default for normalized text embeddings — it ignores magnitude and just measures the angle between vectors. L2 is geometric straight-line distance — the right choice for image or audio embeddings where magnitude carries signal. Dot product, exposed as ZVecMetricType.Ip (inner product), is angle and magnitude combined — useful when the vector norm encodes information like popularity or confidence. Now the rerankers. Multi-vector fusion (RRF / weighted) runs on the untyped IZvecCollection.Query overload — use .Untyped from a typed collection. Pass two or more ZVecQuery values plus a reranker; fusion stays in-process, no external re-ranking service. Product-search uses ZVecRrfReranker and ZVecWeightedReranker for dense + FTS + dual-collection fusion — see slide 19.

06 / HNSW Internals

How HNSW Works

device_hub 06 / HNSW Internals

How HNSW Works

HNSW = stacked graphs (sparse top → dense bottom)

Like the classic hierarchy diagram: search hops greedily inside a layer (solid arrows), then drops to a denser layer (dashed). Layer 0 holds every vector — that’s where you refine nearest neighbours. Link length shrinks as you go down (“decreasing characteristic radius”).

1
Insert

Link each new vector to nearby nodes; some nodes also get promoted to higher layers.

2
Search

Greedy descent from the top: hop to the closest neighbour, then drop one zoom level.

3
Refine

On Layer 0 (all nodes), expand the local neighbourhood and take top-K.

Tunables: M / EfConstruction on [ZVecVector] · efSearch at query time · SDK defaults M=16, EfConstruction=200 · Next slide: how to choose every slot.

Three Steps to a Typed Collection

Install the package, register ZVec in DI, define a POCO with [ZVecVector]. DI OpenMode defaults to OpenOrCreate — restart-safe; no Create=true on first run / false later. See package README: Create vs Open (restart-safe collections).

Dim and Metric come from the embedding model; M and EfConstruction come from how good/expensive you want the HNSW graph. Not random per project.

09 / Multimodal Alignment

How CLIP is Trained

compare_arrows 09 / Multimodal Alignment

How CLIP Learns to Match Images and Text

Contrastive joint training aligns two encoders into one shared vector space — no manual tagging required.

The Problem

Standard text models and image models speak completely different mathematical languages. A text vector for "dog" and an image vector of a dog land in unrelated coordinate spaces. You can't compare them directly.

Contrastive Joint Training

CLIP trains an image encoder and a text encoder simultaneously on ~400M image–text pairs (CLIP paper / WIT). The objective pulls matching pairs closer and pushes mismatches apart — aligning both encoders into a shared space (512-d for ViT-B/32–scale models).

The Result

Both encoders output vectors in the same space. You can match an image file against a raw text string directly — no manual tagging, no captioning step, no intermediate classification.

This is the slide I wish I'd seen when I first encountered CLIP, because the magic isn't the architecture — it's the training trick. Walk through: First, the problem — a standard image classifier outputs a label, not a vector you can compare with text. Text and image models live in separate mathematical worlds. Second, contrastive joint training — CLIP takes an image encoder and a text encoder, runs them both on matching image-caption pairs, and trains them so that the image vector and its matching caption vector are close in space, while mismatched pairs are pushed apart. Do this on 400 million image-caption pairs and both encoders converge into the same 512-dim space. Third, the result — at inference time, you encode an image, encode a text query, compute cosine similarity. No tagging, no classification, no intermediate step. Now let's see this in code.

Live Demo & Loss Geometry
SigLIP (Sigmoid) vs CLIP (Softmax)

CLIP's softmax temperature inflates positive cosines to [0.25..0.45]. SigLIP's pairwise sigmoid loss produces unscaled positives in [0.05..0.18]. Calibrated threshold (MinCosine = 0.03) and FTS bypass ensure zero false rejections.

Crucial architectural takeaways from our forensic probe: 1) Contrastive dual-encoders (CLIP/SigLIP) are trained on (image, text) pairs; text queries match visual image embeddings in joint space. Querying text vectors with text queries causes anisotropic cone collapse where unrelated items have high similarity. 2) True hybrid search routes the text query to Image ZVec (dense visual ANN) and Text ZVec (FTS BM25 on metadata), fused via RRF. 3) Loss geometry: SigLIP uses sigmoid loss without softmax competition, so true positive cosines are ~0.08..0.15; never use high CLIP thresholds like 0.15 on SigLIP. 4) Never let confidence filters purge confirmed FTS keyword matches.
