01 / Foundations

What is Vector Search?

menu_book 01 / Foundations

What is Vector Search?

find_in_page Keyword Search

Keyword / Lexical Search

SQL: WHERE body LIKE '%error%'

Matches exact strings and wildcards. Fails when vocabulary shifts.

"System crash" ✗ "Application breakdown"

These two phrases mean the same thing but share zero keywords — keyword search returns nothing.

hub Vector Search

Vector / Semantic Search

cosine(query_vec, doc_vec) → 0.94

Matches meaning. Synonyms and paraphrases land close in vector space.

"Network issue" ✓ "Connection timeout"

These phrases share no keywords but mean similar things — vector search finds the match.

Three ingredients
memory
Embedding model

Turns text/image/audio into a fixed-length float vector (384–1536 dims).

calculate
Similarity metric

Cosine, L2, or dot product — measures distance in vector space.

speed
ANN index (HNSW)

Graph structure for sub-millisecond top-K nearest-neighbour search.

ZVec.NET · Internal Tech Session 02 / 18
notes Speaker notes
If you search our knowledge base for "system crash" with a SQL LIKE query, you won't find a doc titled "application breakdown" — even though they mean the same thing. Keyword search is dumb about synonyms. Vector search turns text into numbers — a float array called an embedding — and measures geometric distance. Synonyms land close together in vector space, so "system crash" and "application breakdown" become nearby points. The search finds the match. There are three ingredients: an embedding model converts input to vectors, a similarity metric — cosine, L2, or dot — measures distance in that space, and an ANN index like HNSW makes the search fast enough for production, sub-millisecond on top-K queries. Now let's see where we'd actually use this.

03 / The Problem

The Infrastructure Bottleneck

warning_amber 03 / The Problem

The Infrastructure Tax of Vector Search

Every team that wants to ship a vector feature hits the same wall. The database itself is fast — it's everything around it that hurts.

network_check
Friction 01
Network Overhead

Every query is an HTTP/gRPC round-trip to a separate cluster. 5–30ms added latency on every search — even when the index lookup itself takes 1ms. Serialization, TLS handshake, connection pooling — all overhead you didn't have before.

settings_suggest
Friction 02
Operational Complexity

Another Docker cluster to deploy. Access keys to rotate. Firewalls to configure. Version upgrades to schedule. A monthly cloud bill to justify. Each step is a ticket, an outage window, or a 3am page waiting to happen.

shield
Friction 03 · Critical
Security Boundary

Sensitive records leave your application process. Customer data, internal docs, proprietary code — all shipped over the wire to a third-party service. For regulated industries or internal-only data, this is often a non-starter.

What if we could get vector search without any of this?→

ZVec.NET · Internal Tech Session 04 / 18
notes Speaker notes
Vector search itself isn't hard — the algorithm is well-understood and the libraries are mature. What's hard is the infrastructure tax that comes with it. Network overhead — every query pays a round-trip tax to a separate cluster, often five to thirty milliseconds, which usually exceeds the actual search time. Operational complexity — another system to deploy, monitor, upgrade, and debug when it breaks at 3am, plus access keys to rotate and a cloud bill to justify. Security boundary — this is the one most teams underestimate. If you're searching over customer support tickets, internal financial docs, or proprietary code, shipping those vectors to a third-party vector DB means shipping sensitive data outside your trust boundary. For many of our use cases, that's a hard no. So I went looking for a way to do this in-process. That's what ZVec.NET is.

notes Speaker notes
Let's walk the eight index types. HNSW is the default workhorse — sub-millisecond search, 95 to 99 percent recall, works on every runtime we ship. Flat is exact brute force — keep it for tests and small datasets where 100 percent recall matters. IVF clusters vectors into Voronoi cells and lets you tune nprobe to trade recall for speed at scale. The two platform limits are real and the SDK handles them gracefully — it throws PlatformNotSupportedException before the native call, so you get a clean .NET exception with a helpful message instead of a native crash.

In-DB Rerankers — No Extra Service Needed

Two reranker types ship with the SDK, executed natively inside ZVec:

  • ZVecRrfReranker — Reciprocal Rank Fusion. Combines results from multiple sub-queries (e.g. title_vec + body_vec) into one ranked list.
  • ZVecWeightedReranker — Weighted score fusion. Assign per-field weights (e.g. dense 0.7 / FTS 0.3) and let ZVec compute the final ranking.
Multi-Query Overload
// fuse [q1, q2] with RRF, take TopN var hits = col.Query([q1, q2], topk, reranker: new ZVecRrfReranker { TopN = 10 });
ZVec.NET · Internal Tech Session 08 / 18
notes Speaker notes
Three metrics, one enum. Cosine is your safe default for normalized text embeddings — it ignores magnitude and just measures the angle between vectors. L2 is geometric straight-line distance — the right choice for image or audio embeddings where magnitude carries signal. Dot product, exposed as InnerProduct, is angle and magnitude combined — useful when the vector norm encodes information like popularity or confidence. Now the rerankers — this is a feature most vector DBs charge extra for. When you query multiple vectors at once — say, a title vector and a body vector — ZVec fuses the results in native code using RRF or weighted scoring. You pass a reranker to the multi-query overload and ZVec does the rest. No external re-ranking service, no extra latency from a Python sidecar. We'll see this on the RAG slide when we blend dense and FTS results.

06 / HNSW Internals

How HNSW Works

device_hub 06 / HNSW Internals

How HNSW Works

HNSW builds a multi-layer navigable small-world graph. Top layers are sparse (few nodes, long-range connections); bottom layer is dense (every node, short-range connections). Search descends layer-by-layer, narrowing in on the query neighbourhood.

1
Insert

Walk down from the top layer. At each layer, find the nearest neighbours and connect. New nodes get assigned a layer based on a probabilistic decay.

2
Search

Start at the top, greedy descent: at each layer, move to the neighbour closest to the query until no improvement. Drop one layer. Repeat.

3
Refine

At the bottom layer (all nodes), exhaustively check the local neighbourhood for top-K results.

Tunables (on [ZVecVector])
M = 32 // graph degree
EfConstruction = 256 // build-time beam width
efSearch // runtime beam width — higher = better recall, slower
Layer 2 · sparse
Layer 1
Layer 0 · all nodes
arrow_back arrow_back

HNSW is the default index in ZVec — configured via ZVecHnswIndexParam or the [ZVecVector(M=, EfConstruction=)] attribute.

ZVec.NET · Internal Tech Session 09 / 18
notes Speaker notes
Think of HNSW as a zoom-in map. At the top layer, you're looking at the whole country — few cities, long flights between them. You pick the city closest to your destination. Drop a layer: now you're looking at a region — more towns, shorter hops. Pick the closest town. Drop another layer: now you're at street level, every building visible, you walk to the nearest door. That greedy descent is what makes it O(log N) instead of O(N). The two knobs that matter at build time are M — graph degree, higher means more memory but better recall — and EfConstruction, the beam width at insert time. At query time, efSearch trades recall for latency. The defaults — M equals 32, EfConstruction equals 256 — are what the SDK uses if you don't override them on the attribute.

CRUD & Query — IZvecCollection<T>

Inject IZvecCollection<T> anywhere. Typed filters compile to native filter strings — no magic field names. Sync + async variants; async is cancellation-aware.

CRUD (Typed)
public class ProductService(IZvecCollection<Product> products)
{
    public async Task UpsertAsync(Product p) =>
        await products.UpsertAsync(p);

    public async Task DeleteAsync(string id) =>
        await products.DeleteAsync(id);

    public Task<Product?> FetchAsync(string id) =>
        products.FetchAsync(id);

    public Task DeleteExpiredAsync() =>
        products.DeleteByFilterAsync(
            p => p.Category == "expired");
}
QUERY (Typed + Filter)
public async Task<IReadOnlyList<ZVecHit<Product>>> SearchAsync(
    ReadOnlyMemory<float> queryVector,
    string? category = null)
{
    return await products.QueryAsync(
        p => p.Embedding,           // vector field
        queryVector,                // query
        topK: 10,
        filter: category is null
            ? null
            : p => p.Category == category);

How CLIP is Trained

compare_arrows 09 / Multimodal Alignment

How CLIP Learns to Match Images and Text

Contrastive joint training aligns two encoders into one shared vector space — no manual tagging required.

The Problem

Standard text models and image models speak completely different mathematical languages. A text vector for "dog" and an image vector of a dog land in unrelated coordinate spaces. You can't compare them directly.

Contrastive Joint Training

CLIP trains an image encoder and a text encoder simultaneously on millions of image-caption pairs. The training objective pulls matching pairs closer together and pushes mismatched pairs apart — iteratively aligning both encoders into the same 512-dim space.

The Result

Both encoders output vectors in the same space. You can match an image file against a raw text string directly — no manual tagging, no captioning step, no intermediate classification.

ONNX Embeddings in .NET

memory 09 / Pattern · ONNX Embeddings

Run Embedding Models Locally with ONNX Runtime

lightbulb
Use Case Keep the entire pipeline in .NET — no Python sidecar, no model server. Same pattern used by the MAUI sample for offline RAG.
The Pattern

Microsoft.ML.OnnxRuntime runs .onnx models natively in .NET. Download a sentence-transformers model in ONNX format from HuggingFace, run inference, and feed the resulting ReadOnlyMemory<float> straight into the typed UpsertAsync. No Python process, no HTTP hop to a model server — one container, one process.

Three Steps
01

Download model from HuggingFace (e.g. all-MiniLM-L6-v2.onnx, ~90MB)

02

Load with InferenceSession, tokenize input with Microsoft.ML.Tokenizers

03

Run inference, mean-pool over tokens, L2-normalize → 384-dim ReadOnlyMemory<float>

Load · Tokenize · Run · Upsert to ZVec
using var session = new InferenceSession("all-MiniLM-L6-v2.onnx");

// Tokenize + run inference
var tokens = tokenizer.Encode(input);
var inputs = new[] {
    NamedOnnxValue.CreateFromTensor("input_ids", tokens)
};

using var results = session.Run(inputs);
float[] embedding = results.First()
    .AsTensor<float>().ToArray();  // 384-dim

// Hand off to ZVec — typed UpsertAsync
await products.UpsertAsync(new Product
{
    Id = docId,
    Title = title,
    Embedding = embedding   // ReadOnlyMemory<float> implicit conv
});
rocket_launch Why This Matters

End-to-end .NET pipeline · deployable as a single container · no Python/Node sidecar to operate · lower latency (no IPC) · simpler CI/CD. The same pattern works for CLIP, image encoders, audio encoders — anything with an ONNX export. The MAUI sample ships a full offline RAG host on this pattern.

ZVec.NET · Internal Tech Session 17 / 18
notes Speaker notes
The pattern: HuggingFace has hundreds of sentence-transformers models exported as .onnx — download one, point OnnxRuntime at it, tokenize your text, run inference, get a float array. Mean-pool over the token dimension — the model outputs one vector per token; you average them, weighted by the attention mask — then L2-normalize. Now you have a 384-dim vector ready for ZVec — hand it off via typed UpsertAsync. The implicit conversion from float array to ReadOnlyMemory of float is free, so no allocation overhead. Why this is the right default for .NET teams: first, one container, one process — operations stays simple; second, no Python install in production; third, no HTTP hop to a model server, so latency is just model inference time — around 10 to 30 ms on CPU for MiniLM; fourth, the same pattern works for CLIP, image encoders, audio encoders. The MAUI sample in the repo ships a complete offline RAG host built on this pattern.
